# Offer an optional on-device SQLite instance

The first supported release will include an optional `sql:local` instance on a qualified microcontroller. The default segment journal serves devices that collect and forward observations. Select SQLite for a pipe whose users need to read, filter and correct keyed rows while offline. Each pipe has one authoritative local write path. This extends the [segment journal decision](0007-use-segments-for-the-first-supported-journal.md) for a distinct user requirement.

For each committed group of writes on a SQL-backed pipe, one SQLite transaction allocates sequence numbers, appends immutable outgoing records, updates the logical rows under the pipe’s declared keys, and persists the corresponding sequence state. Successful `Pipe.sync()` makes the rows locally readable and the outgoing records available for retry after restart. Custody and destination receipts govern reclamation of outgoing records. Local row retention is a separate policy. A correction to an existing key can leave one current row and two outgoing records.

Qualify the device subset against a stock Meerschaum `sql:local` instance. It includes source-driven and supplied-document `sync`, keyed updates, bounded `get_docs(begin, end, params, limit)` with named-column filters, and `get_sync_time` on the configured axis. Use the same native SQLite integration from MicroPython and native firmware. Qualify a named board, filesystem and SQLite build before publishing durability or performance guarantees. [Evaluation and host reference case](../architecture-evaluation.md#sqlite-on-the-microcontroller)

Persist the configured Pipe definition so reopening by key restores its columns and dtypes. Qualify inclusive `begin`, exclusive `end`, scalar and list-valued column filters, filtered sync times, empty results and read errors. Match the published behavior for supported nullable keys or reject them explicitly on a build that requires non-null keys. Replaying a correction for a supported key must leave one current row.
