# Meerschaum conventions on a microcontroller

Meerschaum’s first-Pipe tutorial asks the user to name a source, a metric and an instance, sync twice, and inspect the rows. That is a good test for a MicroPython or native ESP-IDF application using SQLite. For a collector with only a journal, the equally useful test is to capture two observations with the radio off and later read both from a peer or an ordinary Meerschaum Pipe. The public interface should support both workflows. The segment journal can stay small because collection and forwarding require only ordered records. [First Pipe](https://github.com/bmeares/Meerschaum/blob/v5.1.5/docs/zensical/get-started/bootstrap.md) · [Incremental sync tutorial](https://github.com/bmeares/Meerschaum/blob/v5.1.5/docs/zensical/get-started/incremental-sync.md) · [Device workflows](peer-sync.md)

**Evidence and status.** The reference is the local Meerschaum checkout at tag `v5.1.5`, commit `b2acd7fe79ec02ff9519ec66a74c8b413eaff654`. This review covers its getting-started guides, Python and Rust interfaces, Pipe lifecycle and parameters, connectors, plugin interfaces, API, engine, deployment and operations. The SQLite observations below were reproduced in temporary instances. Device interfaces are release designs. Today this repository implements the v0 codecs and segment inspection. [Upstream reference index](https://github.com/bmeares/Meerschaum/blob/v5.1.5/docs/zensical/reference/index.md) · [Upstream glossary](https://github.com/bmeares/Meerschaum/blob/v5.1.5/GLOSSARY.md) · [Current wire specification](../spec/wire-format.md)

## What to carry over

| Upstream behavior | MicroMeerschaum design consequence |
| --- | --- |
| **A Pipe handle is cheap.** Its connector, metric and optional location identify it on an instance. Constructing the handle can be local. Registration stores its definition. A row table can appear on a later write. [Pipe constructor](https://github.com/bmeares/Meerschaum/blob/v5.1.5/meerschaum/core/Pipe/__init__.py#L400-L427) · [Registration](https://github.com/bmeares/Meerschaum/blob/v5.1.5/meerschaum/core/Pipe/_register.py) | Reopen a local SQL-backed Pipe by the same keys after reboot and recover its declared columns and dtypes. A plugin’s registration defaults apply on provisioning. A new handle or a retry must not overwrite an existing definition. For a provisioned `peer:` target, constructing a handle or inspecting its keys needs zero radio requests. A changed or unknown definition can require an explicit exchange. |
| **A connector can supply rows or host them.** `plugin:name` selects a source. The instance owns the Pipe’s data and metadata. A caller can supply rows directly. [Connectors](https://github.com/bmeares/Meerschaum/blob/v5.1.5/docs/zensical/reference/connectors/index.md) · [Python source plugins](https://github.com/bmeares/Meerschaum/blob/v5.1.5/docs/zensical/docs/python/plugins.md) | A push Pipe such as `Pipe("sensor", "readings")` consumes `sync(df)`. A trusted `plugin:weather` can implement `fetch(pipe, **kw)` for bare `sync()`. Supplied data bypasses fetching. Pass supported bounds to a historical source. A live sensor implements a single observation or frame without learning a query language. |
| **A sync result can be unpacked as `success, message`.** SQL reports row counts when known. A plugin may have no counts to report. [SyncResult](https://github.com/bmeares/Meerschaum/blob/v5.1.5/meerschaum/core/Pipe/_sync.py#L38-L100) | Preserve two-value unpacking on MicroPython. Report the outcome at the selected target. If a multi-chunk call stops, expose the confirmed input prefix separately from rows inserted or updated. An uncertain in-flight commit needs reconciliation by original identity before resubmission. A local success with the radio asleep is sufficient for a local Pipe. |
| **Rows have application-defined identity.** `columns` defines axis and key roles. `indices` adds lookup paths. `upsert` uses the target key for inserts and corrections. Desktop SQL also defines how nullable keys match. [Parameters](https://github.com/bmeares/Meerschaum/blob/v5.1.5/docs/zensical/reference/pipes/parameters.md#columns) · [Nullable keys](https://github.com/bmeares/Meerschaum/blob/v5.1.5/docs/zensical/reference/pipes/parameters.md#null_indices) | SQLite-backed Pipes maintain current rows and immutable outgoing changes in one transaction. A correction can leave one row and two outgoing records. Repeated equal observations on a journal-only Pipe get separate sequences. A retry of either observation keeps its original sequence. Implement key matching for supported columns deliberately, including SQLite’s treatment of NULL. |
| **Documents are a first-class interface.** `get_docs()` avoids a DataFrame dependency. `begin` is inclusive, `end` exclusive, and `params` filters named columns. Row reads and `get_sync_time()` can use the same filter. [Reading data](https://github.com/bmeares/Meerschaum/blob/v5.1.5/docs/zensical/reference/pipes/reading.md) · [Sync-time signature](https://github.com/bmeares/Meerschaum/blob/v5.1.5/meerschaum/core/Pipe/_sync.py#L917-L953) | Accept ordered row dictionaries, equal-length column lists and the single-row convenience. The qualified SQL subset should read bounded dictionaries with scalar equality or a list of accepted values, honor the same filter on sync time, and preserve half-open ranges. Reject an unsupported predicate explicitly. A failed read must remain distinguishable from a successful empty result. |
| **Dtypes, precision and generated values affect data.** The desktop supports schema inference, explicit dtypes, `static`, UTC datetime precision and richer SQL types. `autotime` can assign one value to an entire frame. [Dtypes](https://github.com/bmeares/Meerschaum/blob/v5.1.5/docs/zensical/reference/pipes/dtypes.md) · [Autotime implementation](https://github.com/bmeares/Meerschaum/blob/v5.1.5/crates/meerschaum-engine/src/sync.rs#L1020-L1046) | Specify a portable flat-document profile before freezing a wire codec. Start qualification with null, boolean, signed integer, finite float, text, and an explicitly typed time axis. Preserve null versus text and integer precision across MicroPython, C, Rust and SQL. Document supported conversions and fail an unsupported type or overflow visibly. Keep supplied event time or generate it once at the origin when UTC is valid. Boot and monotonic time remain available when UTC is unknown. |
| **The small dependency surface is intentional.** Meerschaum ships Python over a Rust implementation, optional frame extras and feature-selectable Rust embedding. It tests behavior using fixtures from a released reference implementation. [Zero-dependency base](https://github.com/bmeares/Meerschaum/blob/v5.1.5/docs/adr/0004-zero-dependency-base-wheel.md) · [Rust embedding](https://github.com/bmeares/Meerschaum/blob/v5.1.5/docs/zensical/docs/rust/embedding.md) · [Parity fixtures](https://github.com/bmeares/Meerschaum/blob/v5.1.5/docs/adr/0002-no-python-core-in-the-package.md) | Put device identity, durability and encoding in one portable C implementation shared by MicroPython and native ESP-IDF applications. Bring SQLite only into a build needing ordinary rows. Put native analysis and materialization on the host. Use desktop behavioral cases for the shared Pipe surface alongside the independent C, Rust and Python byte vectors. |

One compatibility edge is visible before the first write. The desktop constructor interprets the literal location strings `"None"` and `"[None]"` as an absent location. v0 device keys can carry either string or an empty location distinctly. Store and deduplicate against the exact original device key, then map it to a configured ordinary Pipe. If two origins or names share an output Pipe, preserve the information needed to distinguish their rows. This lets existing v0 captures round-trip even when desktop names normalize differently. [Desktop normalization](https://github.com/bmeares/Meerschaum/blob/v5.1.5/meerschaum/core/Pipe/__init__.py#L362-L376) · [Device key validation](../core/src/wire.c)

## Copying rows and forwarding records

The desktop `copy pipes` action can copy registrations and optionally rows. With `--sync-data incremental` it uses the destination’s axis watermark and backtrack window. Desktop verification, bounded historical sync and explicit replacement are separate operations. Copying a row table answers which values the target should hold. Forwarding a device journal answers which original observations the receiver can prove it has accounted for. A switched transport, rebatching, or a newer event time at the destination cannot discharge a missing observation. [Copy window implementation](https://github.com/bmeares/Meerschaum/blob/v5.1.5/crates/meerschaum-cli/src/native/manage/copy.rs#L428-L485) · [Sync, verification and replacement](https://github.com/bmeares/Meerschaum/blob/v5.1.5/docs/zensical/reference/pipes/syncing.md)

The reference probe demonstrates the difference on SQLite. It writes ticks 1, 2 and 10000. The first incremental copy transfers all three. The source then corrects tick 1 from 11 to 44. With a backtrack of one axis unit on this integer Pipe, the next successful incremental copy starts at tick 9999. The destination still has 11 at tick 1. The device should give that correction a new outgoing sequence and deliver it on the next connection even though its event time is old. [Reproducible probe](evidence/meerschaum-pipe-reference.py)

This also changes how the built-in materializer should work. Suppose two immutable records in one generation change the same row. A relay delivers the correction first and the original last. Capture both as soon as storage permits. Apply keyed changes in original sequence order within that stream so the old value cannot win. The simplest first implementation can consume the contiguous accounted-for prefix, maintaining a replayable materialization checkpoint. A crash before that checkpoint must allow reapplying the same keyed rows or deduplicating by record identity for append-only output. A custom materializer that merges independent origins supplies its own row keys or conflict rule. [Peer lineage](peer-sync.md#preserving-lineage) · [Raw-capture decision](adr/0004-acknowledge-a-durable-prefix-at-the-destination.md)

### From a sensor to an ordinary Pipe

With the device Pipe API, an application can push a column batch directly to a local journal. A successful return lets it leave the radio asleep until the next upload window. For readings that need local queries and corrections, select `instance="sql:local"` and declare the Pipe’s key columns on the device. [Capture and delivery example](peer-sync.md#capture-now-send-on-the-applications-schedule) · [Device instance](adr/0010-offer-an-optional-on-device-sqlite-instance.md)

```python
from micromeerschaum import Pipe

samples = Pipe("sensor", "temperature", "east")
success, message = samples.sync({"tick": [41, 42], "celsius": [21.4, 21.7]})
if not success:
    raise RuntimeError(message)
```

Suppose the receiver maps this device stream to `("weather", "temperature", "east")` on its SQLite instance with integer `tick` as the datetime axis. After materialization, the following is ordinary Meerschaum Python. An existing application can read the same rows regardless of whether the device reached the receiver directly or via a peer. Multiple origins mapped to one table need a row key that distinguishes them when their sample keys overlap. [Python Pipe reads](https://github.com/bmeares/Meerschaum/blob/v5.1.5/docs/zensical/docs/python/pipes.md) · [Document mapping](adr/0008-include-a-dictionary-to-pipe-path.md)

```python
import meerschaum as mrsm

temperatures = mrsm.Pipe("weather", "temperature", "east", instance="sql:local")
rows = temperatures.get_docs(begin=41, end=43, limit=2)
```

## Receiving device records on Meerschaum 5.1.5

Two devices can complete a delivery offline. When a Meerschaum instance is also a destination, the receiver plugin has two jobs. It acknowledges durable raw capture at that destination and publishes queryable rows through ordinary Pipes. Uploads can continue during a parser outage, and a repaired parser can replay the retained bytes. The Rust crate validates v0 and v1 batches and scans v0 journal segments. The native plugin installs the ingest route and exposes separate replay and status commands. [Install the receiver](../receiver/plugin/README.md) [Peer delivery](peer-sync.md#initial-release-example) · [Destination receipt](adr/0004-acknowledge-a-durable-prefix-at-the-destination.md) · [Receiver code](../receiver/src/lib.rs) · [Archive reader](../receiver/examples/mm_dump.rs)

### The HTTP exchange

**Stock Pipe writes.** `POST /pipes/{connector_keys}/{metric_key}/{location_key}/data` accepts JSON or text parsed into documents. Its ordinary blocking response is a JSON pair such as `[true, "…"]`. With `blocking=false` the request can succeed while work is pending. Meerschaum also has an internal graph-batch receipt containing a selector and a digest. That exchange requires the originating execution callback. A device sending journal bytes needs the plugin’s own route, stream identity and reply. [Registered routes][ops-routes] · [Payload parser][ops-parser] · [Sync result][ops-result] · [Graph-batch receipt][ops-graph-receipt] · [Callback requirement][ops-graph-auth]

**Plugin route.** A packaged Rust plugin can depend on the receiver crate and expose a native route under its own path. The server checks the declared scopes, admits the request, then passes the request body and caller identity to the plugin. The host caps native request bodies at 64 MiB. Choose a transfer budget that fits both endpoints. Install a compatible prebuilt library or build the package on its host, then restart the API to load its routes. A Python host plugin can add a FastAPI route with `@api_plugin`. [Native dispatch][ops-dispatch] · [Route and restart behavior][ops-native-guide] · [Packaging][ops-packaging] · [Python extension points][ops-python]

**Who may send.** A gateway can authenticate over HTTPS with a scoped API key in the `Authorization` header. On the route, bind the authenticated principal to its permitted origins and Pipe keys, including the origins it may forward for. Record the gateway as the observed sender. Choose materializers and output Pipes from an operator-controlled mapping. This permits a relay to carry another origin’s bytes while preserving both identities. [Token authentication and scopes][ops-token] · [Principal fields][ops-principal] · [Lineage](peer-sync.md#preserving-lineage)

### Committing a receipt

Concurrent requests can enter the same plugin. In one storage transaction, check the identity and bytes, retain newly arrived records, record route evidence, apply declared loss and advance the contiguous prefix. Return the receipt after commit. If the destination already holds 1 and receives 3, it can store 3 and still report 1. Receiving 2 then allows it to report 3. A retry on a second route can add route evidence even when all payloads already exist. An equal identity with different bytes is a conflict. [Concurrency][ops-native-guide] · [Prefix and loss](adr/0004-acknowledge-a-durable-prefix-at-the-destination.md) · [Recovery scenario](peer-sync.md#first-implementation-milestone)

The native SDK exposes `host::transaction` with a PostgreSQL advisory transaction lock or SQLite `BEGIN IMMEDIATE`. SQL statement failures can arrive with the success field set to false and must cause the closure to return an error. Inside an API route, starting a host transaction requires `sql:read` and executing writes requires `actions:execute` and permission to run actions. A device with only a custom ingest scope lacks that authority. The released receiver uses a plugin-owned raw store with narrowly provisioned write access and fixed operations over admitted streams. A separate worker can publish to authorized output Pipes. Through the API, Pipe ownership, team visibility and edit rights apply to the worker. A local worker using database credentials is governed by database access, and writes through the Meerschaum Pipe API still honor Pipe locks. [Access boundaries][ops-locks] · [Transaction implementation][ops-tx] · [SQL and route permission rules][ops-tx-permissions]

### Publishing rows and running the host

| Host mechanism | How it applies after raw capture |
| --- | --- |
| Source plugins | A Python or Rust `fetch` hook supplies rows. `register` supplies initial Pipe parameters. A host materializer can read retained raw data and use the ordinary target’s write path. Give each materializer its own checkpoint and stable output keys, including a row discriminator if one observation produces multiple rows. A crash after rows commit and before that checkpoint advances must allow the same input to be processed again. [Python hooks][ops-python] · [Native row writes][ops-host-writes] · [Document materialization](adr/0008-include-a-dictionary-to-pipe-path.md) |
| Streaming | `mrsm sync pipes --listen` drives a streaming source. A native subscription can yield rows with an acknowledgement token. The sink batches by row count, bytes, idle time or latency and acknowledges tokens after the rows commit. Tokens belong to a subscription. A new connection needs the device receiver’s durable prefix for its origin, Pipe and generation. [Listener behavior][ops-listen] · [Commit and acknowledgement order][ops-flush] · [Token lifetime][ops-subscription] |
| Pipelines | Parents and children declare data dependencies. The engine records changed ranges in a ledger and advances each edge’s cursor after the child sync succeeds. A late timestamp can trigger a downstream backfill. Keep raw delivery progress in the receiver and use graph cursors to refresh derived datasets. [Graph planning][ops-pipelines] · [Ledger and edge cursor][ops-ledger] |
| Jobs and Compose | In `mrsm-compose.yaml`, declare output Pipes, named Pipeline members and jobs for the listener or scheduled processing. `mrsm compose explain` previews definitions. `mrsm compose up --dry` writes registrations. `mrsm compose up` can start jobs. `--loop --min-seconds 300` sleeps after each lap. A schedule such as `-s 'every 5 minutes' -d` runs the host job in the background. Device firmware owns its radio wake policy. [Compose behavior][ops-compose] · [Loop and listen][ops-listen] · [Schedules][ops-schedules] |
| Administration | Check output rows in the console, use `mrsm show runs` and `mrsm show run <id>` for per-node outcomes, and inspect `pipe.get_sync_status()` for the most recent Pipe write. A direct sync refuses a sync-locked Pipe. A Pipeline can report success while marking that member locked and using its existing rows. Show the raw prefix and each materializer’s outstanding work separately so operators can locate a stalled delivery. [Console][ops-console] · [Run and Pipe status][ops-state] · [Access and locks][ops-locks] |

The release targets collection, local SQL queries, peer sync and trusted source plugins on the ESP32 so an application can run entirely on the board. Database-specific maintenance, historical verification, arbitrary SQL sources, parameter templates, dependency planning, job supervision, teams, the web console and MCP belong to the ordinary deployment when one is present. Operators can use tags and Compose to organize and schedule the resulting Pipes there. A sensor emitting its first dictionary needs none of that infrastructure. [Host operations index](https://github.com/bmeares/Meerschaum/blob/v5.1.5/docs/zensical/reference/index.md) · [Maintenance](https://github.com/bmeares/Meerschaum/blob/v5.1.5/docs/zensical/reference/pipes/maintenance.md) · [Hosted MCP](https://github.com/bmeares/Meerschaum/blob/v5.1.5/docs/zensical/reference/mcp/index.md)

**Host acceptance case.** Install the receiver on a fresh SQLite deployment, then repeat with concurrent PostgreSQL workers. Submit the same identity over two allowed routes, lose the successful reply, restart the receiver and close a gap out of order. Assert one copy of each original record, both observed routes and the exact receipt after each step. Attempt the same write under a valid token for an unauthorized origin and verify that coverage stays unchanged. Lock the materialized Pipe, accept another raw batch, then unlock and replay. Verify the expected rows and that the previously issued destination receipt still describes the same prefix. [Receiver qualification](adr/0004-acknowledge-a-durable-prefix-at-the-destination.md) · [Upstream crash-after-commit test][ops-crash] · [Locked Pipeline test][ops-lock-test]

## Reference run and qualification

Run this from the repository root with a Python environment containing Meerschaum 5.1.5 and its working CLI. It creates two disposable SQLite instances and disables automatic package installation. The check uses only the built-in document forms.

```sh
python docs/evidence/meerschaum-pipe-reference.py
```

| Observed on desktop 5.1.5 | Acceptance case for the supported device surface |
| --- | --- |
| Constructing a Pipe created no SQLite file. Explicit registration assigned an ID while the row table was still absent. | Construct a peer handle with the radio off. Reopen a provisioned SQL-backed Pipe by key before and after its first row. An unavailable peer cannot be inferred to be an unregistered Pipe. |
| The filtered window `[1, 2)` included tick 1 and excluded tick 2. The newest global tick was 10000, while the newest for sensor `"NA"` was 1. | Apply bounds and filters before the row limit and compute filtered sync time on the selected rows. Keep the delivery cursor independent of either answer. |
| The default SQLite upsert merged two rows with key `(3, None)`. The literal text `"None"` identified a second row. SQLite’s bare UNIQUE constraint would permit multiple NULL keys. | Compare actual content after a correction, a retry and a reopen. If a device build only supports non-null keys, reject null before committing and identify that limitation. |
| An old correction outside the incremental copy window remained absent at the destination. | Upload the correction by sequence, interrupt the reply and retry. Deliver it ahead of the original via another route. Verify two immutable records, one corrected row, both observed routes where applicable, and independent raw and materialization progress. |
| Sending the correction (44) and then the original (11) through ordinary keyed upserts left 11 in the table. Applying the correction last restored 44. | The built-in materializer must respect source order for updates to the same key. Test interruption between row commit and checkpoint, then compare the final row with an uninterrupted replay. |

Pin the upstream version when recording fixtures so an upstream behavior change can be reviewed as a compatibility decision.
