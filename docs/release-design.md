# Initial release design

The first implementation can start with two offline nodes and one Pipe. A sensor commits readings with the radio asleep. Later, its peer durably accepts a batch, the reply gets lost, and both nodes restart. The peer must still have the original readings. The sender must be able to finish that delivery and append the next reading. This is the smallest example that tests both the usefulness of the API and the reason to maintain a journal. [Two-node acceptance test](peer-sync.md#first-implementation-milestone)

## What an application author learns

| Task | Release contract |
| --- | --- |
| Collect readings | Name a Pipe by connector, metric and optional location. Pass a list of rows, equal-length columns or one document to `sync(df)`. Calling `sync()` on a configured `plugin:<name>` Pipe fetches its input. A successful local sync commits the input to the selected store. |
| Send a backlog | Configure one destination and let the application choose when to connect. The framework sends bounded batches and resumes by sequence. A direct write to a provisioned `peer:` instance can send the key with the data. Constructing the handle uses no radio. |
| Query or correct local rows | Opt into `sql:local` on a qualified board. One SQLite transaction commits a group of keyed row changes, its immutable outgoing records and their sequence state. Bounded document reads and `get_sync_time` follow the supported desktop conventions. |
| Use a hosted instance | Install the Meerschaum ingest plugin and configure a mapping to an ordinary Pipe. The receiver commits raw input before issuing its delivery receipt. The materializer can catch up after an outage. A direct operation promising queryable rows succeeds when those rows have committed. |

The default collection target is a single-medium segment journal. The portable C implementation owns record identity, persistence and retry. MicroPython provides the document and source-plugin interface. Native ESP-IDF exposes C and C++ access to the same operations, including caller-owned buffers. Arduino-ESP32 packages that native API for sketches on the same qualified ESP32-S3 board and medium. Firmware owns acquisition, RAM queues, power and radio scheduling. Device SQLite is optional. FlashDB remains a candidate for a specific medium if it demonstrably reduces maintenance and passes the same recovery tests. ## Decisions that protect data

1. **Keep record identity across retries.** One identity is the origin, Pipe key, generation and sequence. Two equal readings can be two real observations. Retrying a transfer must preserve the original identity and bytes. Equal identity with different bytes is a conflict. After a partial local write, report the confirmed input prefix and reconcile any uncertain group against its assigned identities before appending again. A new call that resamples a sensor can create a new observation. [Frame inputs and replay](adr/0008-include-a-dictionary-to-pipe-path.md)
2. **Tie reclamation to a specific delivery.** One cumulative receipt can cover a whole batch. Accept it from an authorized issuer for its role, stream, generation and intended destination. If records 1 and 3 arrive, the receipt stays at 1 until 2 is accounted for. An authorized relay may assume custody offline once it can recover the records and the onward obligation after restart. A route entry or a successful BLE write cannot retire data. [Receipt and custody tests](peer-sync.md#first-implementation-milestone)
3. **Make full storage recoverable.** The default protects previously accepted, unacknowledged records. A Pipe may explicitly favor recent readings. Distinguish a count of samples missed before admission from the sequence range of committed records evicted. Only the latter can account for a sequence gap. Persist loss evidence before discarding the corresponding bytes, retain capacity to record it when the data area is full, and protect data already accepted in custody. [Retention](adr/0002-configure-retention-per-device-pipe.md)
4. **Keep lineage proportional to the job.** Preserve the source identity and distinct observed routes by range. A repeated route can be coalesced, and two routes can deliver one observation. A correction or aggregate produced by a peer is a new record with input provenance. Precision of derivation references, replica lifetimes, automatic replacement of failed peers and conflict resolution for independent editors are later design work. A deployment can build a hierarchy by configuring successive destinations. That requires no topology discovery or network-wide acknowledgement. [Peer destinations and lineage](peer-sync.md#preserving-lineage)

## Implementation order and evidence

1. **Specify the new exchange and prove it on files.** Start with versioned fixtures for saved stream identity, batches, receipts and declared loss. Keep v0 archives and their legacy replies on their existing path. Cut the link after commit, fail a storage barrier, close a gap out of order, reject conflicting bytes and replay a stale receipt after changing generation or destination. Reclaim the last eligible segment and reboot before appending again. The allocator must still know the next sequence. The host test can use opaque payloads while the portable document encoding is specified. [Wire v0](../spec/wire-format.md) · [Host test](peer-sync.md#first-implementation-milestone)
2. **Put an ordinary document through the public APIs.** Specify how the receiver identifies the document encoding or configured binary schema. Pin scalar types, bounds and time representation with cross-language fixtures. Run the same offline exchange on ESP-IDF and MicroPython in both BLE roles, then from an installable Arduino sketch. Exercise relay custody, firmware replacement with pending records, full media and physical power cuts. Measure peak RAM, acquisition stalls and commit latency locally, then backlog drained per radio wake. [Board and migration tests](device-api.md#support-and-qualification)
3. **Qualify row storage and hosted delivery.** Select a SQLite port and medium with checked persistence errors. Compare keyed updates, filters and generated timestamps with desktop Meerschaum. Install the HTTPS receiver on clean SQLite and PostgreSQL deployments. Deliver a correction ahead of the original, lose a reply, and stop between a row write and its materializer checkpoint. Ordered replay must produce the same final row with one copy of each raw record. [SQLite decision](adr/0010-offer-an-optional-on-device-sqlite-instance.md) · [Host acceptance](meerschaum-design.md#receiving-device-records-on-meerschaum-515)

The first milestone runs on a POSIX host with a file-backed writer and direct peer exchange. Independent C and Rust codecs validate the draft v1 formats using shared byte vectors. The remaining milestones include the document codec, device bindings and storage ports, BLE and relay custody, the SQLite instance, the installable receiver and physical durability measurements.
